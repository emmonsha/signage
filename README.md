# Управление экранами

Админка + страницы-плееры (`left`, `right`, `big_wall`). Картинки, PDF и видео приводятся к 1920×1080 автоматически.

## Быстрый старт (Linux + Docker)

Нужны Docker Engine и плагин Compose v2 (`docker compose version`).

### Вариант 1 — одной командой (`install.sh`)

Скрипт `install.sh` делает всё сам: клонирует репозиторий (или берёт текущую папку),
создаёт `.env`, задаёт пароль админки, собирает образ, поднимает контейнер и ждёт
готовности. Он **идемпотентен**: повторный запуск не затирает `.env`, пароль и данные,
поэтому годится и для установки с нуля, и для настройки уже работающего проекта.

```bash
# с сервера — одной строкой (подставьте свой репозиторий):
SIGNAGE_REPO=https://github.com/USER/signage.git \
  curl -fsSL https://raw.githubusercontent.com/USER/signage/main/install.sh | bash

# либо из папки проекта (в том числе распакованного из ZIP):
./install.sh
```

Что можно задать переменными (все необязательны):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `SIGNAGE_DIR` | каталог установки | `~/signage` |
| `SIGNAGE_REPO` | git-URL репозитория | — (в режиме curl обязателен) |
| `SIGNAGE_BRANCH` | ветка | `main` |
| `SIGNAGE_PORT` | порт админки на хосте | `3000` |
| `ADMIN_PASSWORD` | пароль админки (иначе спросит или сгенерирует) | — |
| `ADMIN_USER` | логин локального администратора | `admin` |
| `AUTH_MODE` | `local` / `freeipa` / `both` | `local` |
| `ADMIN_ALLOWED_NETS` | ограничить админку сетью, напр. `192.168.0.0/16` | без ограничений |
| `FREEIPA_*`, `DEPLOY_*` | настройки каталога и автодеплоя (как в `.env`) | — |
| `SIGNAGE_YES=1` | без вопросов (автоматизация) | `0` |
| `SIGNAGE_NO_UP=1` | только собрать, не запускать | `0` |

Пример: развернуть в `/opt/signage`, порт 8080, сгенерировать пароль и ограничить админку сетью:

```bash
SIGNAGE_DIR=/opt/signage SIGNAGE_PORT=8080 ADMIN_ALLOWED_NETS=192.168.0.0/16 \
  SIGNAGE_REPO=<git-url> bash install.sh
```

После запуска скрипт печатает адрес админки и (если пароль был сгенерирован) сам пароль —
сохраните его. Сменить позже: `scripts/reset-password.sh`.

### Вариант 2 — вручную

```bash
cp .env.example .env && chmod 600 .env       # Compose сам читает .env из этой папки
docker compose build

# 1. хэш пароля (скрытый ввод) -> вставьте строку в .env
docker compose run --rm --no-deps signage node hash-password.js

# 2. (рекомендуется) ограничьте админку своей сетью: ADMIN_ALLOWED_NETS=192.168.0.0/16 в .env

docker compose up -d
docker compose ps          # статус должен стать healthy
```

Админка: `http://IP_СЕРВЕРА:3000/admin`

Адреса для HTML5-виджетов в системе публикации: их выдаёт админка — в карточке каждого экрана есть поле
«🔗 Ссылка плеера» с кнопкой **Копировать**. Ссылка содержит секретный токен экрана и выглядит так:

- `http://IP_СЕРВЕРА:3000/player?token=<токен экрана>`

Токен у каждого экрана свой. Имена экранов можно менять в админке (кнопка ✏️ у заголовка карточки) —
на ссылку это не влияет. Кнопка **Перевыпустить** меняет токен: старая ссылка сразу перестаёт работать
(удобно, если ссылка «утекла»). Новые экраны добавляются кнопкой **＋ Экран** в шапке.

Закрепите IP сервера в роутере (DHCP reservation) — иначе после его смены презентации придётся перепубликовывать.

## Видео

Видео загружается так же, как картинка (кнопка «Добавить слайд»; форматы MP4, MOV, MKV, WebM, AVI и др.). Сервер сам конвертирует ролик через ffmpeg:

- контейнер MP4, видео H.264 High (уровень 4.2), `yuv420p`, 1920×1080, постоянная частота кадров (не выше `VIDEO_MAX_FPS`, по умолчанию 60), метаданные в начале файла (`faststart`);
- звук: по галочке «Оставить звук» AAC стерео 48 кГц, иначе дорожка удаляется;
- пропорции не 16:9: вписать с чёрными полями, обрезать по центру или отклонить (тот же выбор, что у картинок); вертикальные ролики и поворот из метаданных телефона обрабатываются;
- предупреждения при низком разрешении, частоте выше лимита, чересстрочном и HDR-видео.

Как это работает в админке:

- Время показа ролика равно его длине и не редактируется. Остальное (даты, порядок, удаление) как у картинок.
- Конвертация идёт в фоне по одному ролику (остальные в очереди), в карточке экрана виден раздел «Обработка видео» с прогрессом. Ролик попадает в эфир, когда готов; удаление отменяет конвертацию.
- Если сервер перезапустили во время конвертации, ролик помечается как прервавшийся: загрузите файл заново. Ошибка ffmpeg показывается в строке ролика.
- Видео нельзя поставить заглушкой, только картинку.

Ограничения и ресурсы:

- Конвертация нагружает процессор (ffmpeg запускается с пониженным приоритетом, но на слабом сервере поставьте `VIDEO_THREADS=2` и `VIDEO_PRESET=veryfast`). Минута 1080p занимает от десятков секунд до нескольких минут в зависимости от процессора.
- Контейнеру дано 2 ГБ памяти. Место на диске: размер файла после конвертации (обычно 5–15 МБ на минуту), оригинал удаляется.
- Через обратный прокси проверьте лимиты тела запроса: для nginx `client_max_body_size 2g; proxy_request_buffering off;` и увеличенные `proxy_read_timeout`/`proxy_send_timeout`. Сам сервер ждёт загрузку до 30 минут.
- **Проверьте воспроизведение на вашей модели плеера до боевого запуска**: потолок H.264 (профиль, уровень, 1080p60) зависит от модели плеера, а правила автозапуска и звука в HTML-виджете могут отличаться от браузера. Для более слабых моделей поставьте `VIDEO_MAX_FPS=30`. Сначала загрузите короткий тестовый ролик со звуком и без.
- Без Docker нужен ffmpeg в системе (`apt install ffmpeg` / `brew install ffmpeg`); без него картинки работают, а видео отклоняется с понятным сообщением. Пути можно задать через `FFMPEG_PATH` и `FFPROBE_PATH`.

## Вход через FreeIPA (LDAP)

Кроме локального пароля админки можно включить вход по учётным записям каталога **FreeIPA**.
Сервер находит пользователя в каталоге и проверяет пароль повторным bind-ом; пароль не сохраняется.

```dotenv
AUTH_MODE=both                       # local | freeipa | both
ADMIN_USER=admin                     # аварийная локальная учётка (режим both)
ADMIN_PASSWORD_HASH=<scrypt-хэш>     # npm run hash-password
FREEIPA_ENABLED=true
FREEIPA_URL=ldaps://ipa.example.com:636
# Либо — адрес по частям (удобно при нестандартных портах); FREEIPA_URL приоритетнее:
# FREEIPA_HOST=ipa.example.com
# FREEIPA_SCHEME=ldaps              # ldap | ldaps (порт 389 → ldap, иначе ldaps)
# FREEIPA_PORT=1636                 # пусто → 636 для ldaps, 389 для ldap
FREEIPA_BASE_DN=dc=example,dc=com
FREEIPA_USER_BASE_DN=cn=users,cn=accounts,dc=example,dc=com
FREEIPA_BIND_DN=uid=signage-bind,cn=users,cn=accounts,dc=example,dc=com
FREEIPA_BIND_PASSWORD=<пароль сервисной учётки>
FREEIPA_USER_FILTER=(uid={username})
```

- `AUTH_MODE`: `local` — только локальный пароль; `freeipa` — только каталог; `both` — каталог,
  а при его недоступности аварийный вход локальной учёткой `ADMIN_USER`. Если не задано — `freeipa`,
  когда `FREEIPA_ENABLED=true`, иначе `local`.
- Сервисная учётка (`FREEIPA_BIND_DN`) нужна для поиска: FreeIPA по умолчанию запрещает анонимный
  поиск. Заведите отдельного пользователя с правом чтения каталога.
- Поддержаны `ldaps://` и `ldap://` + `FREEIPA_STARTTLS=true`. Для самоподписанного CA —
  `FREEIPA_TLS_CA_FILE=/path/ca.crt` (либо `FREEIPA_TLS_REJECT_UNAUTHORIZED=false` только в тестовом контуре).
- Ограничение по группе: `FREEIPA_REQUIRE_GROUP=cn=signage-admins,cn=groups,cn=accounts,dc=example,dc=com`.

### Кто может входить (список допущенных)

В каталоге FreeIPA обычно есть не только ваша команда, но и все остальные сотрудники. Со своим
доменным паролем любой из них смог бы войти в админку, поэтому вход ограничен **списком допущенных**
(файл `data/users.json` на томе; **пароли там не хранятся** — только перечень логинов).

Список ведётся из админки — в панели **«Пользователи»** (кнопка в шапке). Добавляя логин, сервер
проверяет, что такой пользователь есть в каталоге, и подтягивает его имя.

В той же панели видно **активные входы**: кто, откуда (IP, браузер) и когда вошёл. Чужую сессию
можно завершить (например, потерян ноутбук) — потребуется ваш пароль. Себя так завершить нельзя,
для этого есть «Выйти».

Ролей нет: любой, кому разрешён вход, — **равноправный администратор** с полными правами.

- Пока список **пуст** — работает прежнее правило: входит любой сотрудник каталога.
- Как только вы добавили **первую** запись — вход остальным закрывается сам, без правки `.env`.
  Человек с верным паролем, но не из списка, получит отказ «учётная запись не в списке допущенных».
- Если человека убрать из списка, его уже открытая сессия сразу становится недействительной.

Поведение можно зафиксировать явно через `FREEIPA_ACCESS_MODE`:

| Значение | Когда что |
|---|---|
| `auto` (по умолчанию) | список не пуст → пускаем только его; пуст → всех из каталога |
| `list` | всегда только список (заведите хотя бы одного, иначе войти будет некому) |
| `open` | всегда пускать всех из каталога (ограничение выключено, список — только справочник) |

Если в каталоге заведена отдельная группа для вашей команды, проще и надёжнее задать
`FREEIPA_REQUIRE_GROUP`: тогда членство проверяет сам каталог, а список допущенных не нужен
(при обоих ограничениях должны выполняться оба).

Безопасность: пустой пароль отклоняется (LDAP трактует его как анонимный bind и пускает), логин
экранируется по RFC 4515 (защита от LDAP-инъекции), при нескольких совпадениях вход запрещён,
недоступность каталога не даёт доступа, есть ограничение попыток. Полное описание и примеры —
в `docs/03_FREEIPA_AUTH.md`. Тесты: `npm test`.

### Страница входа и значок пользователя

- Поле «Логин» показывается **всегда** — форма одинакова для всех режимов, никаких сюрпризов
  после выхода. В `freeipa`/`both` логин вводит пользователь; в режиме `local` учётка одна,
  поэтому поле предзаполнено `ADMIN_USER` и курсор сразу в пароле. Подсказка о режиме и
  логин подставляются сервером прямо в HTML (форма корректна даже без JavaScript).
- Страница входа — по адресам `/admin` (без сессии) и `/login`.
- В правом верхнем углу админки — **значок пользователя** с выпадающим меню: имя, источник входа
  (FreeIPA/локальная учётка) и кнопка «Выйти». Данные берутся из `GET /api/me`.
- API: `GET /api/me` → `{ success, username, displayName, via }` (`401` без входа).

## Снапшот экрана (что реально показывает)

Кнопка «📸 Снять снапшот» в карточке экрана делает **реальный кадр с плеера** через Local DWS
(`POST /api/v1/snapshot` → скачивание файла) и сохраняет историю в томе (последние N кадров).
Адрес плеера задаётся в админке (поле «IP плеера»), логин/пароль DWS — в `.env`:

```dotenv
PLAYER_DWS_USER=admin
PLAYER_DWS_PASSWORD=<пароль Local DWS>
PLAYER_DWS_SCHEME=http          # http | https
PLAYER_DWS_PORT=80              # 443 для https
SNAPSHOT_ORIGINAL=true   # кадр в оригинальном разрешении
SNAPSHOT_KEEP=20                    # сколько последних кадров хранить на экран
SNAPSHOT_TIMEOUT_MS=15000           # таймаут запроса к плееру, мс
```

Сервер сам ходит к плееру (нужен сетевой доступ сервер → плеер и включённый Local DWS).
Авторизация DWS — Digest (fallback Basic). Для конкретного экрана можно переопределить
логин/пароль: `PLAYER_DWS_BIG_WALL_PASSWORD=…`. Подробнее — `docs/04_SNAPSHOTS.md`.

## Автодеплой «одной кнопкой»

Кнопка «⬆ Обновить систему» в админке обновляет signage до последнего коммита ветки:
контейнер шлёт команду мини-агенту на хосте (`deploy-agent.js`), тот делает `git pull` +
`docker compose up -d --build`. Источник — self-hosted GitLab (deploy key). Всё в `.env`:

```dotenv
DEPLOY_ENABLED=true
DEPLOY_AGENT_URL=http://127.0.0.1:9123
DEPLOY_AGENT_TOKEN=<общий токен с агентом>
```

Установка агента на сервере: `scripts/install-deploy-agent.sh` (systemd-сервис, токен, deploy key).
Контейнер запускается в host-сети: `docker compose -f docker-compose.yml -f docker-compose.deploy.yml up -d --build`.
Подробно — `docs/05_AUTODEPLOY.md`.

## Безопасность

Три уровня, от простого к строгому:

1. **Хэш вместо пароля.** `ADMIN_PASSWORD_HASH` (scrypt, параметры OWASP) — в `.env` лежит не пароль, а его хэш. Открытый `ADMIN_PASSWORD` работает как запасной вариант, сервер предупредит в логе.
2. **Секрет в файле.** Вариант с Docker secrets (хэш читается из `/run/secrets/…`, не виден в `docker inspect` и переменных окружения):
   ```bash
   mkdir -p secrets && docker compose run --rm --no-deps signage node hash-password.js \
     | sed 's/^ADMIN_PASSWORD_HASH=//' > secrets/admin_password_hash
   chmod 400 secrets/admin_password_hash       # должен читаться uid 1000
   docker compose -f docker-compose.yml -f docker-compose.secrets.yml up -d
   ```
   Любой параметр поддерживает суффикс `_FILE` (`ADMIN_PASSWORD_HASH_FILE`, `ADMIN_PASSWORD_FILE`); файл имеет приоритет над переменной.
3. **Ограничение по сетям.** `ADMIN_ALLOWED_NETS=192.168.0.0/16,10.0.0.0/8` — админка, загрузка, удаление и статус отвечают 403 снаружи. Плееры продолжают работать: им открыты только `/player`, `/api/playlist/*`, `/uploads/*`, `/api/heartbeat`, `/healthz`.

Важно про ограничение по сетям:

- Это **второй рубеж**, основной — межсетевой экран хоста или прокси (`ufw`, `nftables`, правила роутера): закрывайте порт для чужих сетей там.
- С опубликованным портом Docker клиенты из LAN сохраняют свой реальный IP, а запросы с самого хоста приходят с адреса моста (`172.x.x.x`) — добавьте `172.16.0.0/12`, если заходите с сервера. В rootless Docker и Docker Desktop исходный адрес может теряться — там фильтруйте на прокси или файрволе.
- За обратным прокси задайте `TRUST_PROXY=1`, иначе сервер увидит адрес самого прокси. Прокси должен перезаписывать `X-Forwarded-For`, а не дописывать присланное клиентом.

## Потерян пароль

Хэш необратим: пароль не «вспоминают», а задают заново. Сброс делается **на сервере** (нужен доступ к docker), старый пароль не нужен:

```bash
scripts/reset-password.sh            # новый хэш -> .env
scripts/reset-password.sh --secret   # новый хэш -> secrets/admin_password_hash (если используете Docker secrets)
```

Скрипт дважды спросит новый пароль (ввод скрыт), посчитает хэш в контейнере, заменит `ADMIN_PASSWORD_HASH` в `.env` (забытый открытый `ADMIN_PASSWORD` тоже удалит, остальные настройки не тронет) и пересоздаст контейнер. Ошибка на любом шаге (пароли не совпали, слишком короткий) ничего не меняет.

**После смены пароля все ранее выданные сессии админки перестают действовать.** Сессии живут в файле на томе и переживают перезапуск (чтобы деплой не выкидывал людей), поэтому каждая сессия помнит «отпечаток» текущего пароля. Смена пароля отпечаток меняет — старые cookie (в том числе украденные) больше не работают. Это же правило закрывает доступ, если человека убрали из списка допущенных.

Без Docker: `npm run hash-password`, замените строку `ADMIN_PASSWORD_HASH=` в `.env` и перезапустите сервер.

Почему сброс не «по почте»: у внутренней админки с одним пользователем нет надёжного второго канала, а письмо превращает доступ к чужому ящику в доступ к админке. Поэтому правило такое: пароль может сбросить тот, кто управляет сервером. Если потерян и доступ к самому серверу, это решается уровнем ниже: консоль виртуальной машины или гипервизора, физический доступ.

## Повседневное

```bash
docker compose logs -f signage         # логи
docker compose restart signage
docker compose down                    # остановить (данные сохраняются в томе)
git pull && docker compose up -d --build   # обновление кода
```

Контейнер сам поднимается после перезагрузки сервера (`restart: unless-stopped`; Docker должен быть включён: `systemctl enable docker`).

### Обновление

Код обновляется пересборкой образа — файлы из `public/` и `*.js` попадают в контейнер
только на этапе сборки:

```bash
git pull
docker compose up -d --build        # пересборка + перезапуск
```

`docker compose restart` **недостаточно**: он перезапускает контейнер со старым образом,
и правки в коде/интерфейсе не подхватятся.

Вход в админку при обновлении **не сбрасывается**: сессии лежат в томе
(`data/sessions.json`), секрет подписи — в `data/.session-secret`. Раньше сессии жили
в памяти процесса, и каждый деплой выкидывал всех на страницу входа.

## Данные и бэкапы

Всё изменяемое хранится в томе `signage_storage` (`/storage`: `data/` — плейлисты, `screens.json` — экраны и их токены, `users.json` — список допущенных к админке, `players.json` — адреса плееров для снапшотов, `sessions.json` — сессии админки, `uploads/` — картинки и видео).

```bash
scripts/backup.sh                      # -> backups/signage-ДАТА.tar.gz (хранится 14 последних)
scripts/restore.sh backups/signage-….tar.gz
```

Добавьте `scripts/backup.sh` в cron, например раз в сутки: `0 3 * * * /opt/signage/scripts/backup.sh`.

### Перенос данных с локальной установки (macOS и т.п.)

Ссылки на картинки в плейлистах относительные, поэтому папки `data/` и `uploads/` переносятся как есть:

```bash
docker compose up -d --build && docker compose stop signage
docker run --rm -v signage_storage:/storage -v "$PWD/старая-папка":/src busybox:stable \
  sh -c 'cp -r /src/data /src/uploads /storage/ && rm -rf /storage/data/tmp && chown -R 1000:1000 /storage'
docker compose start signage
```

## Настройки (.env)

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `ADMIN_PASSWORD_HASH` | хэш пароля админки (рекомендуется) | — |
| `ADMIN_PASSWORD` | пароль в открытом виде (запасной вариант) | — |
| `AUTH_MODE` | источник входа: `local` / `freeipa` / `both` | по FreeIPA, иначе local |
| `ADMIN_USER` | логин локального администратора (режимы local/both) | admin |
| `FREEIPA_*` | вход через FreeIPA (LDAP) — см. раздел «Вход через FreeIPA» | выкл. |
| `FREEIPA_URL` / `FREEIPA_HOST`+`FREEIPA_SCHEME`+`FREEIPA_PORT` | адрес каталога: полным URL или по частям (нестандартные порты) | — |
| `FREEIPA_ACCESS_MODE` | кого пускать из каталога: `auto` / `list` / `open` (см. «Кто может входить») | auto |
| `FREEIPA_TIMEOUT_MS` | таймаут запроса к каталогу (мс) | 5000 |
| `PLAYER_DWS_USER`, `PLAYER_DWS_PASSWORD` | логин/пароль Local DWS плеера для снапшотов | admin, пусто |
| `PLAYER_DWS_SCHEME`, `PLAYER_DWS_PORT` | схема/порт DWS | http, 80 |
| `SNAPSHOT_ORIGINAL` | снимать кадр в оригинальном разрешении | true |
| `SNAPSHOT_KEEP` | сколько последних кадров хранить на экран | 20 |
| `SNAPSHOT_TIMEOUT_MS` | таймаут запроса к плееру (мс) | 15000 |
| `DEPLOY_ENABLED` | кнопка «Обновить систему» (автодеплой) | false |
| `DEPLOY_AGENT_URL`, `DEPLOY_AGENT_TOKEN` | адрес и токен мини-агента деплоя | 127.0.0.1:9123, — |
| `ADMIN_ALLOWED_NETS` | сети, из которых доступна админка (CIDR через запятую) | без ограничений |
| `PORT` | порт на хосте | 3000 |
| `SCREENS` | экраны при **первом** запуске (дальше имена и токены — в `data/screens.json`, правятся в админке) | left,right,big_wall |
| `MAX_PDF_PAGES` | максимум страниц в одном PDF | 50 |
| `MAX_VIDEO_MB`, `MAX_VIDEO_SECONDS` | максимальный размер и длина видео | 2048 МБ, 900 с |
| `VIDEO_MAX_FPS`, `VIDEO_THREADS`, `VIDEO_PRESET` | параметры конвертации (см. «Видео») | 60, авто, medium |
| `TRUST_PROXY`, `COOKIE_SECURE` | для работы за https-прокси (см. ниже) | выкл. |
| `TZ` | часовой пояс контейнера (влияет на время в логах и в файлах) | UTC |
| `SESSION_SECRET` | секрет подписи cookie; нужен только для нескольких копий сервера за балансировщиком | хранится в томе (`data/.session-secret`) |

После изменения `.env`: `docker compose up -d`. Для хэша пароля есть `_FILE`-вариант (см. «Безопасность»).

## HTTPS через обратный прокси

Плееры спокойно работают по http в локальной сети. Если админку нужно открыть по https (например, через Caddy/nginx/Traefik), проксируйте на `127.0.0.1:3000`, передавайте заголовки `X-Forwarded-For` и `X-Forwarded-Proto`, и задайте в `.env`: `TRUST_PROXY=1`, `COOKIE_SECURE=true`. Тогда вход по голому `http://IP:3000` перестанет работать — для плееров оставьте http-адрес в локальной сети или отдельное правило в прокси. Пример для Caddy:

```
signage.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

## Если что-то не так

- Контейнер перезапускается по кругу: `docker compose logs signage` — сервер пишет, что не задан пароль или неверен формат хэша или `ADMIN_ALLOWED_NETS`.
- `docker compose ps` показывает `unhealthy`: чаще всего том недоступен для записи.
- При использовании папки хоста вместо тома (`./storage:/storage`) выполните `sudo chown -R 1000:1000 storage`: контейнер работает от пользователя `node` (uid 1000).
- Секрет-файл не читается: он должен принадлежать uid 1000 или быть читаемым для него (`sudo chown 1000 secrets/admin_password_hash`).
- «Нужна авторизация» сразу после входа: включён `COOKIE_SECURE=true`, а вы открыли админку по http.
- 403 в админке: ваш адрес не входит в `ADMIN_ALLOWED_NETS` (в логе контейнера видно, какой адрес был заблокирован).
- Порт занят: измените `PORT` в `.env`.
- Изменения в коде или интерфейсе не видны: сделан `docker compose restart` вместо
  `docker compose up -d --build` (файлы копируются в образ при сборке).
- Снапшот не снимается: сообщение об ошибке в админке подсказывает причину. Пароль
  Local DWS задаётся в `.env` (`PLAYER_DWS_USER`/`PLAYER_DWS_PASSWORD`), а не в
  админке — сервер ходит к плееру сам.
- Вход по доменной учётке отклонён, хотя пароль верный: строка «не в списке допущенных» — этот
  человек не добавлен в разделе «Пользователи» (см. «Кто может входить»). Если у вас своя группа
  в каталоге, вместо списка можно ограничиться `FREEIPA_REQUIRE_GROUP`.
- Лампочка связи серая, а плеер работает: он открыт по старой ссылке
  `/player?screen=<имя>`. Нужна ссылка с токеном — `/player?token=<токен>` из карточки
  экрана. В карточке появится предупреждение, в логе — строка про «СТАРЫЙ формат».
