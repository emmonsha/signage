# Вход через FreeIPA (LDAP)

Документ описывает, как включить аутентификацию админки signage через каталог
FreeIPA. Вся конфигурация — через `.env`, секреты в репозитории не хранятся.

- Реализация: `freeipa.js` (клиент — библиотека `ldapts`).
- Интеграция: `server.js`, роут `POST /api/login` (и подсказка `GET /api/auth`).
- Список допущенных: `users.js` + `data/users.json`.
- Тесты: `test/freeipa.test.js` (клиент, сеть не нужна), `test/users.test.js` (реестр и режимы),
  `test/ipa-access.test.js` (живой сервер с подменённым каталогом). Запуск `npm test`.

## Как это работает

1. Сервер подключается к каталогу и выполняет **bind сервисной учёткой**
   (`FREEIPA_BIND_DN` / `FREEIPA_BIND_PASSWORD`).
2. Ищет пользователя по фильтру (по умолчанию `(uid={username})`) в `FREEIPA_USER_BASE_DN`.
3. Делает **повторный bind найденным DN с введённым паролем** — это и есть проверка пароля.
   Успешный bind = верные учётные данные. Пароль нигде не сохраняется.
4. Необязательно: проверяет членство в группе (`FREEIPA_REQUIRE_GROUP`, полный DN).

Безопасность учтена:

- **Пустой пароль не отправляется.** LDAP трактует bind с пустым паролем как анонимный и часто
  отвечает «успех» — это классическая дыра «вход без пароля». Отклоняется сразу.
- **Логин экранируется** по RFC 4515 (`Filter.escape`), поэтому `*`, `(`, `)`, `\` не позволяют
  подменить фильтр (LDAP-инъекция).
- **Несколько совпадений → отказ** (`ambiguous`): не пускаем, если логин неоднозначен.
- **Ошибка каталога не «пускает»**: недоступность LDAP не считается успешным входом.
- **Ограничение попыток**: 5 неудач по паре IP+логин и по IP → блок на 15 минут.
- Поддержаны `ldaps://` (TLS сразу) и `ldap://` + StartTLS.

## Режимы (AUTH_MODE)

| Режим | Поведение |
|---|---|
| `local` | только локальный пароль админки (`ADMIN_PASSWORD_HASH` / `ADMIN_PASSWORD`). По умолчанию, если FreeIPA выключен. |
| `freeipa` | только каталог; локальный пароль не используется. |
| `both` | FreeIPA, а при его недоступности/отказе — аварийный вход локальной учёткой `ADMIN_USER`. |

Если `AUTH_MODE` не задан: `freeipa`, когда `FREEIPA_ENABLED=true`, иначе `local`.
В режиме `both` логин `ADMIN_USER` (по умолчанию `admin`) сначала проверяется в каталоге, затем локально —
то есть не мешает одноимённому пользователю FreeIPA.

## Кто может входить (список допущенных)

Проверка пароля в каталоге отвечает на вопрос «тот ли это человек», но не на вопрос «можно ли ему
в админку». В рабочем каталоге FreeIPA обычно есть и все остальные сотрудники — со своим доменным
паролем они бы тоже вошли. Поэтому после успешного bind сервер проверяет **список допущенных**.

- Хранение: `data/users.json` на томе (рядом с `screens.json`). **Пароли не хранятся** — только
  перечень логинов, имя и комментарий.
- Ведение: из админки, кнопка **«👥 Пользователи»** в шапке (появляется только когда вход по каталогу включён).
  Два API: `GET /api/users` (список и текущий режим), `POST /api/users` ({ username, note }),
  `POST /api/users/delete` ({ username, password }) — удаление подтверждается паролем текущего админа.
- При добавлении сервер ищет логин в каталоге: опечатка видна сразу («в каталоге нет пользователя»),
  а имя подтягивается автоматически.

Режим ограничения — `FREEIPA_ACCESS_MODE`:

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | список не пуст → пускаем только его; пуст → пускаем всех из каталога |
| `list` | всегда только список (заведите хотя бы одного, иначе войти будет некому) |
| `open` | всегда пускать всех из каталога; список — только справочник |

Так админ, добавив первую запись в пустой список, сразу закрывает вход остальным — без правки `.env`
и перезапуска. Отказ по списку возвращает 401 с текстом «Нет доступа: учётная запись не в списке
допущенных» (в логе — соответствующий `warn`). В режиме `both` этот отказ не блокирует аварийный
локальный вход `ADMIN_USER`.

Если в каталоге есть своя группа для команды, надёжнее и проще задать `FREEIPA_REQUIRE_GROUP`:
членство проверит сам каталог. Оба ограничения, если заданы, действуют одновременно.

## Адрес каталога и нестандартные порты

Адрес можно задать либо целиком в `FREEIPA_URL`, либо по частям — второе удобно, когда каталог
слушает не на стандартном порту (свой проброс, `ldaps` на необычном порту и т. п.):

```bash
# Вариант А — полный URL (приоритетный, если задан):
FREEIPA_URL=ldaps://ipa.example.com:636

# Вариант Б — по частям:
FREEIPA_HOST=ipa.example.com
FREEIPA_SCHEME=ldaps              # ldap | ldaps; по умолчанию ldap при порте 389, иначе ldaps
FREEIPA_PORT=1636                 # пусто → 636 для ldaps, 389 для ldap
```

Правила: `FREEIPA_URL` побеждает, а если он пуст — берётся `FREEIPA_HOST` (+ схема/порт). Если не
задано ни то, ни другое, сервер откажется стартовать с понятным сообщением. В `FREEIPA_HOST` идёт
только имя или IP — без схемы и порта (иначе ошибка: «порт задайте в FREEIPA_PORT»).
StartTLS по-прежнему управляется только `FREEIPA_STARTTLS` — для нестандартных портов оно
не включается само, чтобы не сломать уже работающие настройки.

## Панель «Пользователи»

Кнопка **«Пользователи»** в шапке админки (когда вход через каталог включён) открывает две части:

1. **Сейчас работают** — активные сессии: имя, источник входа (FreeIPA / локальная), время входа,
   IP и браузер. Видна пометка «это вы». Чужую сессию можно завершить — понадобится ваш пароль.
   Себя завершить нельзя (для этого — «Выйти»).
2. **Кто может входить** — тот самый список допущенных (см. выше): добавление, удаление.

API: `GET /api/users` (список и режим), `POST /api/users` (`{ username, note }`),
`POST /api/users/delete` (`{ username, password }`), `GET /api/users/sessions` (активные сессии),
`POST /api/users/sessions/revoke` (`{ id, password }`).

Наружу отдаётся не сам идентификатор сессии, а его хэш: по нему можно завершить сессию, но нельзя
её угнать. Недействительные сессии (сменился пароль или человека убрали из списка) помечаются
как «недействительна» и завершаются при первом же запросе.

Ролей нет: любой, кому разрешён вход, — равноправный администратор с полными правами.

## Настройка FreeIPA

Сервисная учётка для поиска (по умолчанию FreeIPA запрещает анонимный поиск):

```bash
# на сервере FreeIPA: отдельный пользователь с правом чтения каталога
ipa user-add signage-bind --first=Signage --last=Bind --shell=/sbin/nologin
ipa passwd signage-bind
```

Убедитесь, что админка видит каталог:

```bash
# с хоста, где работает контейнер (порт 389/636 открыт на сервере FreeIPA)
ldapsearch -x -H ldaps://ipa.example.com:636 -D 'uid=signage-bind,cn=users,cn=accounts,dc=example,dc=com' \
  -W -b 'cn=users,cn=accounts,dc=example,dc=com' '(uid=alice)' dn
```

## Настройка `.env`

```dotenv
AUTH_MODE=both                       # freeipa | both | local
ADMIN_USER=admin                     # аварийная локальная учётка (режим both)
ADMIN_PASSWORD_HASH=<scrypt-хэш>     # npm run hash-password

FREEIPA_ENABLED=true
FREEIPA_URL=ldaps://ipa.example.com:636
# Либо — адрес по частям (удобно при нестандартных портах); FREEIPA_URL приоритетнее:
# FREEIPA_HOST=ipa.example.com
# FREEIPA_SCHEME=ldaps              # ldap | ldaps (порт 389 → ldap, иначе ldaps)
# FREEIPA_PORT=1636                 # пусто → 636 для ldaps, 389 для ldap
FREEIPA_BASE_DN=dc=example,dc=com
FREEIPA_USER_BASE_DN=cn=users,cn=accounts,dc=example,dc=com
FREEIPA_BIND_DN=uid=signage-bind,cn=users,cn=accounts,dc=example,dc=com
FREEIPA_BIND_PASSWORD=<пароль сервисной учётки>
FREEIPA_USER_FILTER=(uid={username})
FREEIPA_STARTTLS=false               # для ldap:// поставьте true
# FREEIPA_REQUIRE_GROUP=cn=signage-admins,cn=groups,cn=accounts,dc=example,dc=com
FREEIPA_ACCESS_MODE=auto             # auto | list | open — кого пускать из каталога (см. «Кто может входить»)
```

Применить: `docker compose up -d`. В логе появится строка `Аутентификация: both (FreeIPA: …)`.
При включённом каталоге там же будет виден режим доступа: только список или без ограничения.

### Сертификат (ldaps / StartTLS)

- Публичный/корпоративный CA — ничего делать не нужно.
- Самоподписанный CA — положите файл в контейнер и укажите `FREEIPA_TLS_CA_FILE=/path/ca.crt`
  (через `_FILE`-переменную или смонтированный том).
- Быстрая проверка в тестовом контуре (не для прода): `FREEIPA_TLS_REJECT_UNAUTHORIZED=false`
  (сервер напишет предупреждение в лог).

### Секреты через Docker secrets

Любая переменная поддерживает суффикс `_FILE` (файл имеет приоритет над переменной), например
`FREEIPA_BIND_PASSWORD_FILE=/run/secrets/freeipa_bind_password`.

## Проверка

```bash
npm test                                  # юнит-тесты freeipa.js (25 шт., без сети)
docker compose up -d && docker compose logs -f signage

curl -s localhost:3000/api/auth           # {"mode":"both","username":true}
curl -s -X POST localhost:3000/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","password":"<пароль FreeIPA>"}'   # {"success":true,...}
```

## Интерфейс входа и выход

- Поле «Логин» на странице входа показывается **всегда** — форма одинакова для всех режимов.
  В `freeipa`/`both` логин вводит пользователь; в `local` учётка одна, поэтому поле предзаполнено
  `ADMIN_USER` и курсор сразу в пароле. Режим и логин сервер подставляет прямо в HTML
  (`<body data-auth-mode="…">`, `value="…"`) — форма корректна даже без JavaScript.
- Страница входа отдаётся по `/admin` (без сессии) и по `/login`.
- В шапке админки — значок пользователя с выпадающим меню: имя, источник входа
  (FreeIPA / локальная учётка) и кнопка «Выйти». Данные — из `GET /api/me`.
- `GET /api/me` → `{ success, username, displayName, via }`; без сессии — `401`.
- Источник входа хранится в сессии (`via`) и показывается в меню.

## Известные ограничения

- Пароль проверяется bind-ом; сервер не читает и не хранит хэши паролей пользователей.
- Нет кэширования результатов — каждый вход идёт в каталог (это ожидаемо для редких входов).
- Kerberos/SSO (GSSAPI) не реализованы: вход по логину и паролю каталога.
- Роли/права внутри админки не различаются: любой, кто в списке допущенных, получает полный доступ.
- Список допущенных — это перечень логинов, а не учётные записи: пароль всё равно проверяется в каталоге.
- Требуется `ldapts@^8` (добавлена в зависимости и в образ).
